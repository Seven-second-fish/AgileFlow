# AgileFlow 端到端交互实录

> 这不是规则索引，而是一项真实工作的完整旅程：用户说一句话，AgileFlow 如何形成
> 需求、方案、代码和验收证据，最后交出可以接手的结果。
>
> 排障请看 [TROUBLESHOOTING](../TROUBLESHOOTING.md)。

## 完整实录：从一句话到可交付结果

### 0. 用户提出目标

**用户**

```text
/af 做一个账号密码登录 API，使用 JWT 和 MySQL。
后面都交给你，只有真正需要我时再问。
```

**AgileFlow**

```text
📍 已识别为新功能，将完成需求、方案、实现和验收。

目标
- 用户可以用邮箱和密码登录
- 成功后返回 JWT
- 失败时返回明确且安全的错误信息

接下来
1. 写清验收条件
2. 设计接口、数据和安全边界
3. 实现并运行测试
4. 生成验收报告

你暂时不需要操作。
```

这时还没有写业务代码。AgileFlow 先建立本次工作的可恢复状态。

<details>
<summary>内部记录</summary>

- 创建当前 Run。
- 保存决定方式：AI 可以自动继续。
- 当前步骤进入需求确认。

</details>

### 1. 明确“什么才算做完”

AgileFlow 检查项目现状，生成需求文档：

```text
atlas/requirements/REQ-001-login.md
```

其中包含可以直接验证的条件，例如：

```text
AC-1  正确邮箱和密码 → 返回 200、JWT 和用户基本信息
AC-2  密码错误 → 返回 401，不暴露账号是否存在
AC-3  连续失败达到阈值 → 返回限流结果并留下安全日志
```

随后运行需求检查。

**AgileFlow**

```text
✅ 需求已确认

已经明确
- 登录成功结果
- 失败行为
- 安全限制
- 对应测试方式

下一步：设计接口和实现边界。
```

如果需求缺少范围或验收条件，检查不会通过，AgileFlow 会先修正文档，而不是带着
模糊需求写代码。

### 2. 判断是否需要领域建模

本例只使用已有 User，不新增实体关系或状态机，因此 AgileFlow 说明跳过理由：

```text
建模判断：本次不新增实体、关系、状态机或持久化结构，沿用现有 User。
```

然后进入方案设计，不要求用户学习“建模阶段”命令。

### 3. 形成可以实施的方案

AgileFlow 读取现有项目结构，形成：

```text
atlas/solution/architecture.md
atlas/solution/features/F-001-login.md
atlas/solution/contracts/AC-001-login-api.md
atlas/todo.md
```

**AgileFlow**

```text
✅ 登录方案已完成

核心决定
- POST /api/auth/login
- 密码只通过现有 PasswordHasher 校验
- JWT 使用现有配置，不在日志中输出
- 登录失败统一返回 401
- 连续失败复用现有限流组件

开发任务
- 后端登录接口
- 登录接口单元测试与验收测试

下一步：按方案实现并验证。
```

方案检查确认接口、边界、安全约束和开发任务都存在后，才允许写业务代码。

### 4. 实现：设计 → 编码 → 验证

每个开发任务按相同顺序完成：

1. 先说明复用哪些现有代码、准备修改哪些路径。
2. 再写业务代码。
3. 最后运行编译、单元测试和对应验收测试。

本例产生：

```text
atlas/dev/T-001-login-BE.md
src/auth/LoginController.*
src/auth/LoginService.*
src/auth/LoginService.test.*
test/ac/login.*
```

开发记录中保存了真实命令和结果：

```text
命令：npm test -- LoginService
结果：exit 0，12 passed

命令：npm run build
结果：exit 0

命令：npm test -- test/ac/login
结果：exit 0，AC-1/AC-2/AC-3 PASS
```

**AgileFlow**

```text
✅ 实现完成

已修改
- 登录 Controller 和 Service
- 密码错误与限流处理
- 单元测试和验收测试

验证结果
- 编译通过
- 单元测试 12 项通过
- 需求 AC-1～AC-3 全部通过

下一步：整理最终验收报告。
```

只写“测试通过”不算完成；命令、退出码和对应验收条件必须可以追溯。

### 5. 验收与交付

AgileFlow 汇总已经运行过的证据，生成：

```text
atlas/tests/REQ-001-login-验收报告.md
atlas/tests/README.md
```

**最终回复**

```text
✅ 登录 API 已交付

交付内容
- 邮箱密码登录接口
- JWT 返回与安全错误处理
- 登录失败限流
- 单元测试和需求验收测试

验收
- AC-1 登录成功：PASS
- AC-2 密码错误：PASS
- AC-3 连续失败限流：PASS
- 编译：PASS

主要文件
- src/auth/LoginController.*
- src/auth/LoginService.*
- test/ac/login.*
- atlas/tests/REQ-001-login-验收报告.md

需要你处理
- 无
```

用户拿到的不只是代码，还能从 `atlas/` 查到目标、设计选择、修改过程和验收依据。

### 6. 换一个对话继续

如果工作在中途关闭，新对话只需输入：

```text
/af
```

AgileFlow 会读取当前 Run、任务进度和已经保存的文件，从未完成的位置继续，不会重新
做已经通过的步骤。

## 同一套流程的常见变化

### 希望每个关键决定都由你确认

```text
/af 做一个登录 API，每个关键决定先让我确认
```

AgileFlow 会在需求和方案等关键位置等待你确认。你随时可以说：

```text
后面都交给你
```

之后它会在检查通过后自动继续，质量要求不变。

### 修改已有项目

```text
/af 修改登录模块的超时处理
```

AgileFlow 先局部分析登录模块。只有代码证据表明 Session、权限或共享配置与它不可分，
才扩大到直接上下游；不会因为仓库已有代码就默认全量盘点。

### 先听建议，不实施

```text
/af 项目变慢了，先分析瓶颈并给我几个方向，不要修改
```

返回内容包括：

- 当前证据
- 核心不确定性
- 2～4 个候选方向
- 每个方向的收益、成本和风险
- 推荐方向

默认不写代码、不创建需求，也不保存探索文档。

### 一个很小的修复

```text
/af 首页标题拼错了，直接改掉
```

AgileFlow 会直接修改并验证，不为一行文案启动完整交付流程。

### 中途改变已有需求

```text
登录成功后不要回首页，改成返回上次浏览页。
```

AgileFlow 会先更新已有验收条件，检查受影响的方案、任务和代码，再重新验证相关范围；
不会只改代码而留下过期文档。

### 需要用户提供资源

```text
⏸️ 需要你提供：支付平台测试商户号
完成后回复：已配置测试商户号
```

资源未提供时不会伪造通过。用户完成后，AgileFlow 从被阻塞的位置继续。

### 一次提交多条验收问题

```text
登录跳转不对、错误提示缺失，还想增加短信登录。
```

AgileFlow 会逐条分类：

- 已有要求但实现错误 → 修复并回归。
- 原有要求漏写 → 先补验收条件，再改实现。
- 短信登录属于新能力 → 拆成新需求，不混进普通 bug。

## 用户不需要操作的内部机制

以下内容用于保证可靠性，不是使用前提：

- `AF_DECIDE`：记录由 AI 自动继续还是等待用户确认。
- `AF_STEP`：记录当前执行位置。
- `agileflow-dispatch.json`：多 Agent 的执行记录。
- `runs/<runId>/`：产物摘要、步骤历史和检查回执。
- 开发任务内部的 `①②③`：对应本示例中的“设计 → 编码 → 验证”。

普通用户只需说清目标、查看结果、在确实需要时提供决定或资源。
